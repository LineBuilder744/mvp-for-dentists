# CAD: клиентский кабинет и управление заказами

Django 5.2 LTS, Python 3.12+. Форма заказа — одна страница из трёх блоков:
конструкция, её параметры, сканы и проверка перед отправкой.

## Локальный запуск

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver 0.0.0.0:8000
```

Кабинет: `/orders/`, создание: `/orders/new/`, команда: `/admin/`.
Регистрация: `/accounts/register/`. Вход требует подтверждения email;
локально письмо со ссылкой выводится в терминал сервера. Есть восстановление
пароля. Для настоящей почты задать SMTP из `.env.example`.
`.env` автоматически не загружается: для локального shell можно использовать
`set -a; source .env; set +a`. Не коммитить секреты и локальную базу.

## Конструкции

- Коронка: один или несколько зубов, материал, полная анатомия / Cutback / каркас.
- Мост: отдельные опоры и промежуточные зубы, материал. В этой версии минимум
  две опоры по краям, непрерывный участок одной челюсти. Консоли и другие
  нестандартные случаи требуют отдельного согласования вне стандартной формы.
- Вкладка / накладка: зубы, Inlay / Onlay / Overlay, материал.
- Имплантная коронка: Ti-base или готовый установленный абатмент.
  Параметры Ti-base появляются только в первом случае. Неизвестные значения
  переводят заказ в «Требуется уточнение». Команда заполняет недостающие
  параметры в админке и подтверждает уточнение перед принятием в работу.

Выбор зубов — 32 постоянных номера FDI (11–18, 21–28, 31–38, 41–48).
Количество сервер вычисляет из выбранных позиций; присланные извне количество
и цена не используются. В одном заказе только одна услуга / однородный набор.
Исходный справочник моделей челюстей сохранён для истории, но выключен для
новой формы. Существующие CASE-номера сохранены; новые номера — CAD-000001 и т. д.
Номера уникальны, пропуски в последовательности допустимы.

## Организации, тарифы и акция

Каждый клиент входит в `accounts.Organization`. Самостоятельная регистрация
создаёт новую организацию без акции. Совпадение введённых названий не объединяет
кабинеты. Подключать коллег к существующей организации может только администратор
через поле «Организация / доступ» пользователя после проверки принадлежности.
При миграции старые аккаунты разделены на отдельные организации — автоматического
объединения по неуникальному названию нет. Перевод аккаунта в организацию даёт
ему доступ к её заказам; прежние заказы сами не перемещаются.

Администратор задаёт базовую цену за единицу в «Услугах» или индивидуальный
тариф организации. Индивидуальный тариф имеет приоритет. Цена умножается на
количество единиц, в мосте считаются и опоры, и промежуточные зубы.
Числовых тарифов по умолчанию нет: если тариф не задан, показывается
«Стоимость уточняется». Такой заказ можно создать, но нельзя начать производство
до предложения и согласования стоимости. После создания заказа сохраняется
снимок тарифа; изменение справочника не меняет старые заказы.

Акцию включает администратор, задавая организации остаток бесплатных коронок
(например, 3). Лимит общий для всех её аккаунтов, применяется только к обычным
коронкам. Единицы резервируются при создании заказа с блокировкой записи
организации, возвращаются при отмене до принятия в работу. Повторная отправка
и исправления не расходуют их повторно. Саморегистрация акцию не выдаёт.

Для нестандартного случая администратор вводит общую новую цену и обоснование.
Заказ приостанавливается; клиент любой разрешённой учётной записи организации
подтверждает точную предложенную сумму. Пока согласования нет, начало работы
и выдача результата блокируются. Подтверждение цены и результата не означает
получения денег. Полученную оплату команда отмечает отдельно вручную.

## Команда и выдача

Пользователь с ролью «Дизайнер», `is_staff=True`, подтверждённым email видит
только назначенные заказы — в кабинете, админке и при скачивании файлов.
Роль «Администратор» вместе с `is_staff=True` даёт полный доступ к заказам,
организациям, тарифам и назначениям. Superuser тоже администратор.
Старая команда при миграции получает роль администратора.

Рабочий порядок: назначить дизайнера → проверить комплектность и стоимость →
«В работе». Только тогда выставляются время принятия и ориентир +24 часа.
До проверки заказа точный срок автоматически не обещается.
Внутренний статус «На проверке качества» клиенту отображается как «В работе».

Результат загружается как черновик. Затем специалист выбирает файл в поле
публикации и ставит «Я проверил выбранный STL…». Проверка сохраняет автора
и дату. Без неё публикация и переход в «Готов» недоступны. После исправления
нужно загрузить, проверить и опубликовать новую версию. Старые версии сохраняются.
Клиент может приложить STL или JPG/PNG к запросу исправления.

## Файлы и безопасность

Рабочая челюсть обязательна; отсутствие антагониста / прикуса показывает
предупреждение. Для Ti-base можно отметить scanbody на рабочем скане вместо
загрузки дубликата. Дополнительные файлы необязательны.
Есть drag-and-drop, обычный выбор, прогресс и сохранение выбранных файлов при
ошибке формы. Полная перезагрузка / закрытие вкладки не сохраняет локальный выбор.

STL: до 200 МиБ, проверяются бинарная / ASCII-структура и размер; это не CAD-проверка
геометрии. Изображения: JPG/PNG до 10 МиБ и 20 мегапикселей, проверяются Pillow.
Лимит: 10 исходных файлов на заказ; результаты хранятся версионно.
Файлы закрыты в `PRIVATE_STORAGE_ROOT`, общедоступного media-маршрута нет.
На скачивании всегда проверяется организация / назначение дизайнера.
Клиент видит исходники отдельно от опубликованных результатов и может скачать
результат до оплаты. История статусов, цены, срока и выдачи сохраняется с автором;
доступ к карточкам и скачивание, включая отказы, записываются в журнал.

Ограничения запросов используют общую БД и действуют для всех процессов:
40 POST в минуту на аккаунт (до входа — по IP), 120 запросов расчёта,
5 ГиБ переданных данных в час, 20 ГиБ файлов на организацию, 2 ГиБ на HTTP-запрос.
Настраиваемые значения см. в `.env.example`. Учёт объёма запросов опирается
на проверенный HTTP-сервером Content-Length; reverse proxy должен также
ограничивать поток, число частей multipart, время загрузки и свободное место.
Доверие к произвольному X-Forwarded-For / X-Forwarded-Proto не включено.
Авторизацию и ограничение запросов обязательно проверить с production proxy.

## Бэкап и восстановление

Локальный SQLite: команда делает согласованный снимок БД и добавляет только
файлы, на которые ссылается этот снимок, с SHA-256-манифестом. Архив имеет права 0600.

```bash
python manage.py backup_cad --output /workspace/backups/cad-2026-10-16.tar.gz
python manage.py restore_cad --archive /workspace/backups/cad-2026-10-16.tar.gz --target /workspace/restored/check-2026-10-16
```

Восстановление выполняется только в новый каталог, проверяет контрольные суммы,
целостность SQLite и наличие всех файлов. Рабочая база не перезаписывается.
Проверенный автотест восстанавливает заказ и его STL в изолированный каталог.
Для реального переключения остановить запись, проверить восстановленную копию,
сохранить текущую версию, заменить БД и настроить закрытый путь к восстановленным
файлам, затем выполнить `check` и прогон скачивания с отдельными аккаунтами.

Ежедневное расписание на сервере заказчика (пример cron для SQLite, пути заменить):

```cron
0 3 * * * cd /srv/cad && .venv/bin/python manage.py backup_cad --output /srv/cad-backups/cad-$(date +\%F).tar.gz
```

Хранить резервные копии отдельно от основного диска, в РФ, с ограниченными правами
и шифрованием. Срок хранения архивов согласовать с заказчиком.
В облачной dev-среде cron и внешнее хранилище не настроены.

PostgreSQL включается переменными `POSTGRES_*`. Команды выше намеренно работают
с SQLite. Перед production для PostgreSQL настроить ежедневный `pg_dump` / WAL
и snapshot закрытого хранилища на инфраструктуре заказчика: остановить запись
на время согласованной копии, включить файлы из снимка БД, затем проверить
восстановление базы и файлов вместе в отдельном окружении. Здесь PostgreSQL
и production-восстановление не проверялись.

Удаление закрытых заказов по согласованному сроку хранения:

```bash
python manage.py purge_orders --older-than-days 365
# Только после проверки списка и согласования срока:
python manage.py purge_orders --older-than-days 365 --execute
```

Число 365 — пример, не установленная политика. Без `--execute` ничего не удаляется.
Активные заказы не затрагиваются. Бэкапы имеют отдельную политику удаления.

## Проверки

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
```

STL-загрузки отдельно: `python manage.py test orders.test_stl_uploads`.
Тесты проверяют бинарный и ASCII STL, все назначения сканов, запись на диск,
уникальные обезличенные пути, совпадение содержимого при скачивании и отказ
для пустых / повреждённых файлов. Реальную частную модель можно проверить
без её добавления в Git:

```bash
CAD_TEST_STL_PATH=/private/path/sample.stl python manage.py test orders.test_stl_uploads
```

Без этой переменной пропускается только проверка внешней модели; синтетические
STL тестируются всегда. Исходные модели и имена с персональными данными в
тестовые фикстуры репозитория не включать.

Дополнительный Playwright-прогон: установить Node.js и `playwright`, запустить
dev-сервер, затем `node tests/browser/orders.cjs`. Нужен Chromium; путь задаётся
`CAD_BROWSER_BIN` (по умолчанию `/usr/bin/chromium`). Прогон разрешён только на
dev-базе с DEBUG=1: создаёт уникальные временные аккаунты / тарифы и удаляет их
после завершения. Проверяет конструкции, расчёт, сохранение файлов после ошибки,
админку, проверку качества, изображение к исправлению, согласование цены
и мобильные карточки 320 / 390 px.

## До запуска с настоящими данными

Настроить `DJANGO_DEBUG=0`, случайный `DJANGO_SECRET_KEY`, конкретные hosts и
CSRF origins, WSGI-сервер, HTTPS, SMTP, PostgreSQL и закрытое хранилище в РФ.
В production включены secure-cookie, перенаправление на HTTPS и HSTS.
`python manage.py collectstatic` собирает публичную статику отдельно от сканов.
Проверить реальные STL, лимиты загрузки, журналирование, ежедневный бэкап,
восстановление и согласованный срок удаления файлов / журналов / архивов.
Эта разработческая среда не является подтверждённым размещением данных в РФ.

Юрист заказчика должен согласовать договор с лабораториями, распределение ролей,
политику данных, сроки хранения, уведомление Роскомнадзора и квалификацию CAD-услуги.
Отсутствие ФИО не делает STL автоматически анонимными. Реальные данные пациентов
до выполнения условий запуска в эту dev-среду не загружать.
Автоматической передачи файлов в Dentbird / AI / зарубежные сервисы нет.
AI-дизайн, 3D-редактор, DICOM, All-on-X, индивидуальные абатменты и эквайринг
не включены в стандартную форму.
