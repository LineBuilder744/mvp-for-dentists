# Стоматологический CAD — Django

Первый этап по ТЗ v2.0: база клиентов, база заказов, аккаунты и роли,
закрытые STL, уникальные CASE-номера. Добавлен простой кабинет для проверки
основы и Django-админка для команды. Это ещё не полный MVP из документа.

## Запуск

Python 3.12+, Django 5.2 LTS.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

Кабинет: `/orders/`, регистрация: `/accounts/register/`, команда: `/admin/`.
Администратор создаётся со своим email и подтверждённым аккаунтом.
Клиенты регистрируются самостоятельно; пароли хранятся как хеши Django.
До подтверждения email вход закрыт. Ссылка подтверждения действует три дня
и активируется отдельной кнопкой, чтобы почтовый сканер не подтвердил её автоматически.
Локально письма выводятся в терминал сервера. Откройте ссылку из письма.
Восстановление пароля также использует email.

Настройки читаются из переменных окружения. `.env.example` — образец,
он не загружается автоматически. Для локального использования его можно
скопировать в `.env` и экспортировать: `set -a; source .env; set +a`.
Не помещайте реальные секреты в репозиторий.

## Данные

Одна реляционная база, отдельные связанные таблицы:

- `accounts.User`: email, имя, тип клиента, организация, подтверждение email, права.
- `orders.Service`: включаемый справочник из пяти услуг, заполняется миграцией.
- `orders.Order`: клиент, задание, CASE-номер из неизменяемого ID, отдельные статусы обработки и оплаты, сроки.
- `orders.OrderFile`: закрытый путь, назначение, размер, автор, версия и публикация.
- `orders.Comment`: сообщения в заказе.
- `orders.OrderEvent`: история с датой и автором, внутренние события скрыты от клиента.

Локально используется `db.sqlite3`. При заданном `POSTGRES_DB` включается
PostgreSQL с параметрами из `.env.example`. Проверки в этой среде выполнены
на SQLite; PostgreSQL необходимо проверить перед развёртыванием.

## Заказы и файлы

Клиент создаёт и видит только свои заказы. Фильтр по статусу и поиск по
CASE-номеру. Повторная отправка той же формы возвращает существующий заказ.
Смена статусов проходит через `orders/services.py`, с проверкой переходов
и записью истории. Номер при корректировке сохраняется. CASE-номера уникальны,
но последовательность может иметь пропуски.

Временные правила первой формы, которые нужно согласовать с CAD-командой:
рабочая челюсть обязательна для всех услуг; антагонист и прикус необязательны;
для имплантата нужны система, scanbody, основание и STL scanbody;
для модели нужна челюсть, для остальных услуг — номера зубов FDI.
Количество: 1–32 единицы; дополнительные исходники: до 10 на заказ.
Список обязательных сканов и лимиты являются начальными допущениями.

Поддержаны бинарный и ASCII STL, до 200 МиБ на файл. Проверяется структура,
но не CAD-качество. JPG/PNG-пояснения пока не реализованы. Большие и реальные
сканы нужно проверить с командой. Форма показывает прогресс загрузки.
STL можно перетащить в область нужного поля или выбрать обычной кнопкой;
формат, размер и количество файлов проверяются до отправки.
Не загружайте ФИО и другие прямые идентификаторы пациентов.

Файлы сохраняются в `private_uploads/` (или `PRIVATE_STORAGE_ROOT`), без
публичного media-маршрута. Скачивание только через проверку прав на сервере.
Черновики результатов скрыты от клиента. Предыдущие версии сохраняются.
В карточке заказа исходники находятся в разделе «Ваши файлы», а опубликованные
готовые STL — в разделе «Результаты CAD», начиная с самой новой версии.
Скачивание опубликованного результата доступно до оплаты.

В админке откройте заказ: загрузите результат и сохраните; отдельным
сохранением выберите файл в поле публикации. Затем можно установить «Готов».
После корректировки требуется публикация новой версии. Подтверждение
клиентом переводит заказ в «Завершён», оплату — в «Ожидает оплаты».
Получение денег отмечает команда вручную. Тарифов и онлайн-оплаты нет.
При дополнительной обработке обязательна причина, срок становится неизвестным;
новый конкретный срок команда вводит следующим сохранением. История сохраняется.

## Проверки

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
```

Тесты покрывают подтверждение email, восстановление пароля, хеширование,
чужой доступ к карточке/файлам/действиям, повторную отправку, откат при ошибке,
отключённые услуги, валидацию STL, скрытые результаты, версии и подтверждение
без автоматической отметки оплаты.

## Перед публикацией

Выставить `DJANGO_DEBUG=0`, случайный `DJANGO_SECRET_KEY`, конкретные
`DJANGO_ALLOWED_HOSTS`, SMTP и HTTPS. Dev-сервер не использовать в production.
Настроить ограничение попыток входа и отправки писем на reverse proxy,
лимит запросов/загрузок и защиту от переполнения диска; лимит тела запроса должен
учитывать несколько файлов по 200 МиБ. Передача `X-Forwarded-Proto` доверяется
только контролируемому proxy; настройка доверия сейчас намеренно не включена.
В production собрать статику через `python manage.py collectstatic`.
Базу и файловое хранилище разместить в РФ на инфраструктуре заказчика.
Включить ежедневный согласованный бэкап базы и закрытого каталога, затем проверить
восстановление обоих вместе. Инфраструктура и бэкапы здесь не развёрнуты.
